# Maintain a verification skill

## Adoption and authority

Source, changes and verification limits are in [provenance.json](provenance.json);
retain the upstream [LICENSE](LICENSE). Invocation remains explicit. Scheduled or
PR-triggered invocation needs separately authorized automation. Follow the
repository's planning and confirmation rules. This skill does not authorize
commits, publication, merges, tool installation, or changes to remote, account,
agent, or protected CI configuration. Report unavailable prerequisites as
`blocked`; do not claim unexecuted verification passed.

A feature map rots the moment the app changes. This skill is the upkeep loop for a skill generated by `/create-verification-skill` (or any project-local verification skill with a feature map). The unit of rigor is the feature, not every sentence: cover every feature file from source and exercise every feature live, without terminalising every bullet.

## Outcomes

Pick one, and say which:

- **clean**: every feature got source and live coverage; nothing worth shipping. No branch, no PR.
- **changed**: one reviewable change contains proven doc, harness, or map corrections; publish only within existing authorization.
- **blocked**: coverage could not finish or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

Only edit the verification skill's own directory (its SKILL.md, generated features/ projections, and any harness scripts it owns) and the explicitly registered feature-owned verification descriptors from which its map is generated. Do not move feature-specific scenarios into the shared skill or edit implementation/tests/fixtures through that descriptor allowance. Never edit product code during a run: a behavior the map describes that the app no longer does is either doc drift (fix the map) or a product regression (report it, don't paper over it in docs).

## Independent requirements and functional boundaries

Compare observed behavior with approved requirement and contract IDs before
classifying drift. A changed implementation cannot silently redefine an expected
outcome. Include renamed/deleted files, shared modules, contracts and configuration
when finding affected features. Refresh evidence only after rerunning it against
the current revision; an edited date or hash is not proof of execution.
Check the feature's enforced purity and immutable-state boundary, property-test
seeds/counterexamples, targeted mutation results and actual CI gates. Report
missing or weakened enforcement as a product/infrastructure gap outside this
workflow's edit scope. Do not rewrite expectations, disable checks, add source
comments or suppressions, or report unavailable mandatory scenarios as passing.

## Pass

0. **Locate the target.** Find the verification skill to maintain: the project-local skill whose body has launch/drive sections and a feature map (canonically `.agents/skills/verify-*/`, exposed through the repository's approved harness discovery configuration). Several candidates → ask which one; none → stop and point at `/create-verification-skill` instead of inventing a target.

1. **Index hygiene.** Reconcile the complete independently required feature registry, feature-owned verification descriptors and generated map index. Fix missing, extra, duplicate or dead references and regenerate projections. Every required feature must appear; record unexecuted mandatory scenarios as blocked.

2. **Source wave.** Use read-only source readers per feature when delegation is supported and authorized; otherwise inspect each feature serially and record that independent source review was unavailable. Each explains "how does this user-facing feature work?" from source, flags likely doc drift with citations, and returns one concise live-verification recipe. Children never drive the app and never edit files. Return shape: feature summary / source entry points / likely drift or none / one recipe.

3. **Reconcile.** Every registered feature and authoritative descriptor has a returned summary, or an explicit blocked reason. Merge overlapping recipes into as few app states as practical. Spot-check cited drift; don't re-prove clean claims. Sweep recent churn for user-facing surfaces missing from the map: require a concrete source path before calling one missing.

4. **Live pass.** Required even when source looks clean. The coordinator owns all driving; follow the verification skill's own launch model: one long-lived instance driven serially for servers and UIs, or a fresh isolated session per drive for short-lived CLIs (the skill's Launch section decides, not this one). Exercise every feature at least once, and hold three invariants the whole pass, whatever the failure: (1) never drive an instance you haven't health-checked since it last did something surprising: doctor before first drive, doctor on each fresh session where sessions are the unit, doctor again after any failed drive, and where doctor can't see the failure (a wedged UI state on a healthy process), reset to a known state or relaunch rather than hoping; (2) evidence captured so far survives every cleanup, checked at its named location, not assumed; (3) nothing a drive started outlives that drive's usefulness: failed-iteration residue is cleaned whether the session is stuck, exited, or shared (for a shared instance, clean the residue, not the instance). A doctor failure caused by skill drift is drift: fix it under edit scope and retry once: restart whatever the fix invalidated, nothing more: before calling the pass `blocked`. A feature that can't be reached is `blocked-unreachable` only with the concrete prerequisite (auth, entitlement, OS, external state) and the route attempted; if the map omits that prerequisite, that's drift. Any harness fix from triage gets re-driven live before it ships. Final teardown happens after the last drive of the run: including those re-proofs: so nothing outlives the run (evidence stays, per the skill).

5. **Triage.** A description that disagrees with independent approved requirements is doc drift; correct it to those requirements. An implementation disagreement alone is a product finding until the requirements establish otherwise. Working behavior the harness can't drive → harness gap, fix it; a harness fix follows the same helpers rule as generation (scripts executable, invocation documented in the skill body). App behavior that's actually broken → product gap; record it for the user, keep it out of this PR.

6. **Prepare or stop.** For changed: prepare one reviewable change of proven corrections and reread every changed file. Follow existing authorization and required confirmation before committing or publishing. For clean or blocked: report the outcome and coverage honestly; do not create a PR automatically.

Keep concise run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a scratch location; don't commit them.
