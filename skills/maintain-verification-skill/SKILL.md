# Maintain a verification skill

## Adoption and authority

Source, changes and verification limits are in [provenance.json](provenance.json);
retain the upstream [LICENSE](LICENSE). Invoke for an authorized request or
approved automation. The retained upstream `disable-model-invocation` field is
not a demonstrated cross-harness control. Follow repository authorization and
policy; this skill grants no commit, publication, installation or settings access.
Report missing prerequisites as `blocked`; never claim unexecuted checks passed.
Consumer rules determine colocation, functional purity and comment policy.

A feature map rots the moment the app changes. This skill is the upkeep loop for a skill generated by `/create-verification-skill` (or any project-local verification skill with a feature map). The unit of rigor is the feature, not every sentence: cover every feature file from source and exercise every feature live, without terminalising every bullet.

## Outcomes

Report coverage per feature. The overall result is blocked if any mandatory journey is blocked; list proven corrections separately so partial progress stays visible:

- **clean**: every feature got source and live coverage; nothing worth shipping. No branch, no PR.
- **changed**: one reviewable change contains proven doc, harness, or map corrections; publish only within existing authorization.
- **blocked**: coverage could not finish or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

Only edit the verification skill's own directory (its SKILL.md, generated features/ projections, and any harness scripts it owns) and the explicitly registered feature-owned verification descriptors from which its map is generated. Do not move feature-specific scenarios into the shared skill or edit implementation/tests/fixtures through that descriptor allowance. Never edit product code during a run: a behavior the map describes that the app no longer does is either doc drift (fix the map) or a product regression (report it, don't paper over it in docs).

## Independent requirements and functional boundaries

Compare observed behavior with approved requirement and contract IDs before
classifying drift. A changed implementation cannot silently redefine an expected
outcome. Include renamed/deleted files, shared modules, contracts and configuration
when finding affected features. Refresh evidence only after rerunning it against
the current revision; an edited date or hash is not proof of execution.
Check the consumer's applicable boundary, property/mutation and CI requirements.
Report missing mandatory enforcement as an infrastructure gap outside this edit
scope. A missing optional gate does not invalidate unrelated evidence. Follow
local comment policy; never rewrite requirements or disable checks for a pass.

## Pass

0. **Locate the target.** Find the verification skill to maintain: the project-local skill whose body has launch/drive sections and a feature map (inspect the approved discovery configuration and existing `.agents/skills/`, `.claude/skills/`, `.pi/skills/` and `.opencode/skills/` locations; preserve the canonical target). Several candidates → ask which one; none → stop and point at `/create-verification-skill` instead of inventing a target.

1. **Index hygiene.** Reconcile the complete required feature inventory and existing map. When the consumer has feature-owned descriptors and a generator, update those sources and regenerate projections. Otherwise maintain the canonical local map. Fix missing, extra, duplicate or dead references. Every required feature must appear; record unexecuted mandatory scenarios as blocked.

2. **Source wave.** Use read-only source readers per feature when delegation is supported and authorized; otherwise inspect each feature serially and record that independent source review was unavailable. Each explains "how does this user-facing feature work?" from source, flags likely doc drift with citations, and returns one concise live-verification recipe. Children never drive the app and never edit files. Return shape: feature summary / source entry points / likely drift or none / one recipe.

3. **Reconcile.** Every registered feature and authoritative descriptor has a returned summary, or an explicit blocked reason. Merge overlapping recipes into as few app states as practical. Spot-check cited drift; don't re-prove clean claims. Sweep recent churn for user-facing surfaces missing from the map: require a concrete source path before calling one missing.

4. **Live pass.** Required even when source looks clean. The coordinator owns all driving; follow the verification skill's own launch model: one long-lived instance driven serially for servers and UIs, or a fresh isolated session per drive for short-lived CLIs (the skill's Launch section decides, not this one). Exercise every feature at least once, and hold three invariants the whole pass, whatever the failure: (1) never drive an instance you haven't health-checked since it last did something surprising: doctor before first drive, doctor on each fresh session where sessions are the unit, doctor again after any failed drive, and where doctor can't see the failure (a wedged UI state on a healthy process), reset to a known state or relaunch rather than hoping; (2) evidence captured so far survives every cleanup, checked at its named location, not assumed; (3) nothing a drive started outlives that drive's usefulness: failed-iteration residue is cleaned whether the session is stuck, exited, or shared (for a shared instance, clean the residue, not the instance). A doctor failure caused by skill drift is drift: fix it under edit scope and retry once after restarting only resources invalidated by the fix. If it still fails, report `blocked`. A feature that can't be reached is `blocked-unreachable` only with the concrete prerequisite (auth, entitlement, OS, external state) and the route attempted; if the map omits that prerequisite, that's drift. Any harness fix from triage gets re-driven live before it ships. Final teardown happens after the last drive and any repeated proof, so nothing outlives the run (evidence stays, per the skill).

5. **Triage.** A description that disagrees with independent approved requirements is doc drift; correct it to those requirements. Use approved requirements or the authorized change request to distinguish intentional changes from regressions. When no independent expectation exists, record the observed behavior and seek confirmation for changing an expectation; do not call observation alone a verified requirement or automatically declare a regression. Working behavior the harness can't drive → harness gap, fix it; a harness fix follows the same helpers rule as generation (scripts executable, invocation documented in the skill body). App behavior that's actually broken → product gap; record it for the user, keep it out of this PR.

6. **Prepare or stop.** For changed: prepare one reviewable change of proven corrections and reread every changed file. Follow existing authorization and required confirmation before committing or publishing. For clean or blocked: report the outcome and coverage honestly; do not create a PR automatically.

Keep concise run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a scratch location; don't commit them.
